1. Пользователи и объекты
`users` (вместо раздельных `admin` и `client`)

- `id` (UUID, PK) — уникальный идентификатор.
- `full_name` (VARCHAR) — ФИО сотрудника.
- `login` (VARCHAR, UNIQUE) — логин для входа.
- `password_hash` (VARCHAR) — хэш пароля (например, bcrypt).
- `role` (ENUM: `ADMIN`, `INSPECTOR`) — роль пользователя.
- `is_active` (BOOLEAN) — флаг активности (для блокировки уволенных сотрудников без удаления истории их отчетов).

**Почему объединили:** Админ и инспектор имеют одинаковый набор полей для авторизации. Единая таблица упрощает систему входа (один эндпоинт `/login`), управление токенами и позволяет в будущем легко добавить роль руководителя (только просмотр дашбордов).

`locations` (справочник объектов)

- `id` (UUID, PK)
- `name` (VARCHAR) — название объекта (например, «Цех №4»).
- `address` (TEXT) — адрес.
- `target_lat` / `target_lon` (DECIMAL) — плановые координаты объекта.

**Почему вынесли из `visit`:** Выносить объекты в отдельную таблицу правильнее, чем писать адрес текстом в каждом визите. Это избавит от опечаток и позволит в админке строить аналитику: _«На каком объекте чаще всего находят проблемы?»_.

2. Конструктор шаблонов (самая важная часть)

Чтобы шаблон имел четкую структуру, поддерживал разные типы ответов (текст, оценка, выбор из списка, фото) и дашборды, его нужно разбить на **две связанные таблицы**.

`templates` (шапка шаблона)

- `id` (UUID, PK)
- `name` (VARCHAR) — название шаблона (например, «Еженедельный осмотр оборудования»).
- `description` (TEXT) — инструкция для инспектора.
- `version` (INT) — номер версии шаблона.
- `is_archived` (BOOLEAN) — скрыт ли шаблон из создания новых проверок.

`template_fields` (пункты/вопросы внутри шаблона)

- `id` (UUID, PK)
- `template_id` (UUID, FK -> `templates.id`) — привязка к шаблону.
- `order_index` (INT) — порядковый номер вопроса на экране телефона.
- `title` (VARCHAR) — текст вопроса или название проверяемого узла.
- `field_type` (ENUM: `TEXT`, `RATING_1_5`, `YES_NO`, `SELECT`) — тип ответа.
- `options` (JSONB, nullable) — варианты ответов, если выбран тип `SELECT` (например, `["Исправно", "Требует ремонта", "Критично"]`).
- `is_required` (BOOLEAN) — обязателен ли ответ для закрытия визита.
- `require_photo_on_issue` (BOOLEAN) — требовать ли фото, если выявлена проблема.

**Почему так:** Если хранить вопросы шаблона отдельными строками в `template_fields`, админка сможет легко строить графики по конкретным пунктам (например, средняя оценка по пункту «Чистота зоны»). А колонка `version` защитит старые отчеты: если админ отредактирует шаблон, создастся версия №2, а уже назначенные визиты по версии №1 не сломаются.

3. Выезды и результаты проверок

`visits` (назначенный визит)

- `id` (UUID, PK)
- `name` (VARCHAR) — название проверки.
- `template_id` (UUID, FK -> `templates.id`) — какой шаблон использовать.
- `location_id` (UUID, FK -> `locations.id`) — куда ехать.
- `admin_id` (UUID, FK -> `users.id`) — кто назначил.
- `inspector_id` (UUID, FK -> `users.id`) — кто выполняет.
- `scheduled_at` (TIMESTAMPTZ) — плановая дата и время для календаря.
- `completed_at` (TIMESTAMPTZ, nullable) — фактическое время закрытия визита.
- `fact_lat` / `fact_lon` (DECIMAL, nullable) — реальная геометка инспектора при отправке отчета.
- `status` (ENUM: `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `OVERDUE`).
- `updated_at` (TIMESTAMPTZ) — время последнего изменения (нужно для синхронизации с мобильным приложением).

`visit_answers` (ответы на пункты проверки)

- `id` (UUID, PK) — генерируется на мобильном устройстве (UUIDv4).
- `visit_id` (UUID, FK -> `visits.id`) — к какому визиту относится ответ.
- `field_id` (UUID, FK -> `template_fields.id`) — на какой именно вопрос шаблона дан ответ.
- `value` (TEXT) — сам ответ (текст, цифра оценки или выбранный вариант).
- `has_issue` (BOOLEAN) — флаг «Выявлена проблема» (для быстрой фильтрации проблем в админке и на дашборде).
- `comment` (TEXT, nullable) — пояснение инспектора к проблеме.

`media_files` (фотографии и вложения)

- `id` (UUID, PK) — генерируется на мобильном устройстве.
- `visit_id` (UUID, FK -> `visits.id`) — привязка к визиту.
- `answer_id` (UUID, FK -> `visit_answers.id`, nullable) — привязка к конкретному пункту чек-листа.
- `s3_key` (VARCHAR) — путь к файлу в облачном хранилище (MinIO / S3).
- `file_type` (VARCHAR) — `image/jpeg`, `video/mp4` и т.д.
- `created_at` (TIMESTAMPTZ) — точное время съемки на устройстве.

4. Три главных архитектурных правила, заложенных в эту схему

5. **Использование `UUID` вместо автоинкремента (`1, 2, 3...`):**  
    Поскольку приложение работает в **офлайне**, телефон должен сам создавать ID для ответов (`visit_answers`) и фотографий (`media_files`) еще до связи с сервером. `UUID` гарантирует, что при синхронизации у двух разных инспекторов не совпадут ID записей.
6. **Хранение времени в формате `TIMESTAMPTZ`:**  
    Этот тип данных в PostgreSQL сохраняет время вместе с часовым поясом (в UTC). Если админ в Москве назначит визит на 10:00, инспектор в другом часовом поясе увидит корректное локальное время у себя в календаре.
7. **Разделение ответов (`visit_answers`) и медиа (`media_files`):**  
    К одному пункту проверки инспектор может прикрепить 0, 1 или 5 фотографий. Отдельная таблица `media_files` позволяет не ограничивать количество фото и загружать их в S3 независимо от текстовых ответов.
