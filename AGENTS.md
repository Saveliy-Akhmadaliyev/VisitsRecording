# AGENTS.md

Контекст для AI-агентов (OpenCode и др.), работающих в этом репозитории.

## Проект

Мобильный инструмент для полевых сотрудников: фиксация проверок на объектах по шаблонам (фото, оценки, проблемы) + веб-админка для планирования и контроля. Заказчик: ООО «ПЛАЗМА ДИНАМИКА».

Первоисточники (не удалять и не переименовывать):
- `Требования/` — требования заказчика и решения куратора
- `Сущности для бека.md` — модель данных (схема БД)
- `идеи/Возможный crud.md` — контракт REST API для админки

## Архитектура и поток данных

Monorepo:

| Пакет | Стек | Роль |
|---|---|---|
| `backend/` | Kotlin + Ktor + Exposed + PostgreSQL (Flyway) | REST API + JWT: шаблоны, визиты, результаты, пользователи |
| `admin/` | React + TypeScript (Vite) | Создание шаблонов, назначение визитов, просмотр результатов, дашборд, календарь |
| `mobile/` | Android, Kotlin + Jetpack Compose | Приложение полевого сотрудника |
| `docs/` | — | Схема архитектуры, спецификации, гайды для персонала (часть сдачи, не опционально) |

Поток данных: админка создаёт Visit по Template и назначает исполнителю из списка → мобильное приложение забирает назначения при синке (pull, не push) → исполнитель заполняет форму офлайн (Room) → при появлении сети WorkManager отправляет результаты и медиа на бек → результаты видны в админке. Медиа лежат в MinIO (S3), бек хранит только метаданные.

## Backend

- Таблицы Exposed: `backend/src/main/kotlin/ru/plasmadynamics/visits/tables/`; миграции Flyway: `backend/src/main/resources/db/migration/`, применяются автоматически при старте приложения.
- Схема БД = `Сущности для бека.md`, контракт API = `идеи/Возможный crud.md`. Отклонения от схемы БД (зафиксированы по итогам обсуждения, все — в миграции V2):
  - `updated_at` добавлен в `locations`, `templates`, `template_fields` — для delta-sync с мобилкой.
  - `templates.origin_id` — все версии одного шаблона ссылаются на id первой версии (группировка в списке админки).
  - Статус `CANCELLED` вместо `OVERDUE`: «просрочен» вычисляется на лету (PLANNED + `scheduled_at < now`), в API возвращается как статус `OVERDUE`.
  - Сид-пользователи для разработки: `admin`/`admin123` (ADMIN), `inspector`/`inspector123` (INSPECTOR).
- Аутентификации пока нет, `/api/admin/*` открыт; `admin_id` визита до появления JWT — первый активный ADMIN (TODO в коде).
- `PUT /api/admin/templates/{id}` создаёт новую версию (новый UUID, version+1), старую архивирует — редактирования строк версий нет.
- Новые отклонения от первоисточников фиксировать в этом файле.
- Конфиг — переменные окружения: `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`, `PORT` (дефолты совпадают с docker-compose.yml).

## Команды

- `docker compose up -d` — PostgreSQL (:5432) + MinIO (:9000 API, :9001 консоль), нужны для запуска бека
- `cd backend && ./gradlew run` — запуск API на :8080 (проверка: `GET /health`)
- `cd backend && ./gradlew build` — сборка + тесты; `./gradlew test` — только тесты
- Для `./gradlew` локально нужна Java 17+. Без Java: `docker run --rm --user $(id -u):$(id -g) -e GRADLE_USER_HOME=/tmp/gradle -v $PWD/backend:/work -w /work gradle:8.10.2-jdk17 gradle --no-daemon build`

## Зафиксированные решения

- Мобилка — нативный Android (Kotlin), не кроссплатформа (решение куратора).
- Бек — Kotlin + Ktor (один язык на бек и мобилку).
- Админка — React + TypeScript (решение: самая богатая экосистема для таблиц, графиков и календарей; код проверяется запуском).
- Offline-first — критерий приёмки: локальная БД, очередь отправки, идемпотентные запросы, конфликты last-write-wins на уровне полей.
- Template версионируется: каждая редакция — отдельная строка в `templates` (новый UUID, version+1); уже назначенные визиты ссылаются на старую версию и не ломаются.
- UUID для `visit_answers` и `media_files` генерируются на телефоне до отправки — повторная отправка при синке не создаёт дублей (upsert по PK).
- Язык: код, идентификаторы, коммиты — English; документация, гайды, этот файл — русский.

## Словарь домена (использовать в коде и API)

- Template — шаблон проверки; TemplateField — пункт шаблона
- Visit — выезд на объект (назначение); ответ на пункт — VisitAnswer
- Finding — проблема (VisitAnswer с `has_issue = true`)
- Location — объект (место проверки)

## Критерии приёмки (из `Требования/description.txt`)

- Офлайн-режим + последующая синхронизация
- Полное соответствие утверждённым UX/UI макетам
- Чек-лист сдачи: создание отчёта, прикрепление медиафайлов, отсутствие блокирующих дефектов
- ИБ: интеграция с корпоративным бэкендом, TLS, Android Keystore, приватное хранилище медиа
